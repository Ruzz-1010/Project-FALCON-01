# DOST Major Revision Baseline — 2026-10-10

Status: active documentation baseline for the revised Project FALCON thesis proposal and prototype planning.

## Approved proposal direction

Project FALCON is now documented as a compact, low-cost, event-driven coastal buoy proposal. The design responds to the DOST panel request to simplify the mechanical body, reduce the buoy size, reduce the budget, and avoid unnecessary continuous network transmission.

## Core system scope

The revised buoy has five required core subsystems plus the controller:

1. **Water pressure sensing** — main input for pressure-based wave/water behavior analysis.
2. **Wind sensing** — wind speed and wind direction monitoring; this is part of the core proposal, not an optional add-on.
3. **GPS positioning and security** — exact buoy position, drift monitoring, geofence/security checks, and recovery support.
4. **Battery and solar power** — rechargeable battery, solar panel, charge controller/regulator, and battery monitoring for runtime validation.
5. **Internet communication module** — Wi-Fi for laboratory/near-shore validation and LTE/4G for remote cloud upload when field internet is required.
6. **ESP32 controller** — reads sensors, filters data, detects events, buffers offline records, and schedules uploads.

## Mechanical baseline

- Use a shorter single-pipe / single-tube buoy body with a compact float instead of a tall frame, large tower, or complex outrigger layout.
- Keep the center of gravity low through ballast and battery/electronics placement.
- Keep the top section small and sealed for the ESP32, power regulation, GPS antenna, internet antenna, and optional beacon.
- Use a protected stilling tube or pressure-sensor mount so wave pressure can be sampled without exposing the sensor body to direct impact.
- Treat older large-body, tower, outrigger, and heavy Bay Station drawings as legacy references unless a page explicitly says they are retained for comparison.

## Electronics and communications baseline

- ESP32 remains the required buoy controller for local sampling, event detection, buffering, and upload scheduling.
- Cloud-first communication is allowed when internet is available: Wi-Fi for laboratory/near-shore tests and LTE/4G module for remote field trials.
- LoRa and a large local Bay Station are optional fallback or legacy paths, not the default revised architecture.
- The dashboard/backend may run on the cloud, a laptop, or the existing edge service during validation, but the buoy should not require a mini PC.

## Event-driven telemetry rule

The ocean is never still, so normal waves must not trigger one upload per wave. The ESP32 samples water pressure, wind, GPS, and battery/solar state locally, calculates short-window baselines, and uploads only:

- a regular summary every 1–5 minutes during normal operation;
- an immediate packet when water pressure, wind speed/direction, GPS displacement, buoy tilt, battery/solar status, sensor health, or connection state crosses a validated threshold;
- queued records after reconnecting from an internet outage.

This reduces data use, modem duty cycle, and battery size while still preserving important event history.

## Battery and power baseline

The smaller battery is acceptable only because the revised system uses sleep, local sampling, scheduled summary uploads, and event-triggered modem activity. Final battery size must be based on measured ESP32, pressure sensor, wind sensor, GPS, internet module, and battery-monitor current rather than estimates alone.

## Sensor and budget baseline

The required proposal list must include water pressure, wind, GPS, battery/solar, and internet communication options. Lower-cost alternatives are acceptable only if the validation limits are clearly stated.

Acceptable alternatives include:

- pressure: low-range submersible pressure transmitter, 0–5 V / 0–10 V pressure transmitter, RS485/Modbus pressure transmitter, protected Blue Robotics pressure sensor, or a lower-cost demonstrator sensor for bench validation;
- wind: combined anemometer/wind vane, separate cup anemometer plus vane, or lower-cost DIY reed-switch/potentiometer wind sensor for proposal-level costing;
- GPS: NEO-6M or similar low-cost GPS for position/security, with higher-grade modules as upgrade options;
- battery/solar: Li-ion/LiFePO4 battery, solar panel, solar charge controller, buck/boost regulation, fuse/protection, and battery monitor or voltage-divider fallback;
- internet: ESP32 Wi-Fi for bench/near-shore validation, LTE/4G module for remote cloud upload, and LoRa only as fallback when internet is not viable.

All procurement lists should show item purpose, estimated Philippine peso cost, where it can be bought, and what validation is required before claiming field readiness.

## Documentation handling

Active Markdown and thesis files should follow this baseline. Archived files are retained only for traceability and should not be used as the current design unless they explicitly point back to this revision.
