# DOST Major Revision Baseline — 2026-10-10

Status: active documentation baseline for the revised Project FALCON thesis and prototype planning.

## Approved direction

Project FALCON is now documented as a compact, low-cost, event-driven buoy concept. The design direction responds to the DOST panel request to simplify the mechanical body, reduce the buoy size, reduce the budget, and avoid unnecessary continuous network transmission.

## Mechanical baseline

- Use a shorter single-pipe / single-tube buoy body with a compact float instead of a tall frame, large tower, or complex outrigger layout.
- Keep the center of gravity low through ballast and the battery/electronics placement.
- Keep the top section small and sealed for the ESP32, power regulation, antenna, and optional beacon.
- Use a protected stilling tube or pressure-sensor mount so wave pressure can be sampled without exposing the sensor body to direct impact.
- Treat older large-body, tower, outrigger, and heavy Bay Station drawings as legacy references unless a page explicitly says they are retained for comparison.

## Electronics and communications baseline

- ESP32 remains the required buoy controller for local sampling, event detection, buffering, and upload scheduling.
- Cloud-first communication is allowed when internet is available: Wi-Fi for laboratory/near-shore tests and LTE/4G module for remote field trials.
- LoRa and a large local Bay Station are optional fallback or legacy paths, not the default revised architecture.
- The dashboard/backend may run on the cloud, a laptop, or the existing edge service during validation, but the buoy should not require a mini PC.

## Event-driven telemetry rule

The ocean is never still, so normal waves must not trigger one upload per wave. The ESP32 samples locally, calculates a short-window baseline, and uploads only:

- a regular summary every 1–5 minutes during normal operation;
- an immediate packet when pressure, tilt, vibration, displacement, tamper, battery, sensor health, or connection state crosses a validated threshold;
- queued records after reconnecting from an internet outage.

This reduces data use, modem duty cycle, and battery size while still preserving event history.

## Battery and power baseline

The smaller battery is acceptable only because the revised system uses sleep, local sampling, scheduled summary uploads, and event-triggered modem activity. Final battery size must be based on measured ESP32, sensor, modem, and dashboard-upload current rather than estimates alone.

## Sensor and budget baseline

The preferred pressure approach is still a low-range submersible pressure transmitter or equivalent protected pressure sensor, but the documentation must list lower-cost alternatives and validation gates. Acceptable alternatives include 0–5 V / 0–10 V pressure transmitters, RS485/Modbus pressure transmitters, Blue Robotics pressure sensors for bench or protected tests, ultrasonic/ToF distance sensing inside a stilling tube for controlled prototypes, float potentiometer/encoder concepts for low-cost demonstration, and motion-only event detection when pressure sensing is temporarily unavailable.

All procurement lists should show item purpose, estimated Philippine peso cost, where it can be bought, and what validation is required before claiming field readiness.

## Documentation handling

Active Markdown files should follow this baseline. Archived files are retained only for traceability and should not be used as the current design unless they explicitly point back to this revision.
